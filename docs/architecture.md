# Architecture

CodeHelm is a local CLI orchestrator. Model calls are limited to planning, implementation, documentation, review, and DesignFlow mockup adapters. Scheduling, budgets, and quality decisions are deterministic Python over SQLite.

The package version is `0.1.0`. The behavior below is what the code does now.

## Control plane

- **Planning:** a provider-neutral adapter returns a structured Epic and Stories. The plan is validated locally (IDs, dependencies, cycles) before anything is dispatched.
- **Deterministic engine:** task transitions, the dependency-aware scheduler, attempt and concurrency limits, budget admission, and the quality contract.
- **Adapters:** Claude Code, Codex, Gemini, and Cursor Agent (`cursor`, model from `CODEHELM_CURSOR_MODEL`, default `auto`) CLIs behind one provider interface. The default transport is the CLI. An opt-in HTTP transport for `claude`, `codex`, and `gemini` only is off unless `transport="http"`. It has no default host, model, or token, does not fall back to the CLI, and is not a spending cap.
- **State:** SQLite in `.codehelm/state.db`. Task rows, dispatch claims, budget reservations, and quality evidence live outside the model context.
- **Execution:** one Git worktree per coding task. Worktrees are file isolation, not a container sandbox.
- **DesignFlow:** a screen or form spec is rendered to an HTML mockup. Inline comments are stored locally. `designflow revise --execute` sends the queued comments to a provider and renders the next revision only from JSON that validates. The review server binds to `127.0.0.1` and does not launch a provider. Ported from firstmate's lavish.
- **Integrations:** optional Jira Cloud REST and GitHub pull requests via `gh`. Neither is required to run the engine. Creating a pull request does not merge it and does not run `gh pr ready`. `pr-create` reads `pr_ready` from the working directory's `.codehelm/quality.yaml`. The pull request stays a draft unless `--ready` is set or that value is true. `--draft` forces a draft and wins over both. A missing file, an omitted key, or null stays false. A non-boolean fails policy load. The dry-run line names that same draft or ready choice and does not push. `publish_pr` and `LifecycleEngine.create_pull_request` default `draft=True` and do not read `pr_ready`; the CLI passes the chosen flag. `merge-ready` is off unless `auto_merge: true`, and even then it merges only an open pull request whose gates passed, whose decision required human approval, and whose checks are all success. It does not pass `--auto` or `--admin`, and it does not complete the story. An explicit `jira-transition` command posts one transition id; a dry run does not call Jira. The scheduler posts one only when `jira_transitions` maps the new state and the story has a `jira_key`. That stays off, and dry-run, unless `jira_transition_execute` is true. A failed post is stored and reported. `schedule-durable` merges a recorded pull request only when `auto_merge` is true. The plain `schedule` command does not merge, and a merge does not complete the story.

## Task lifecycle

Agent execution persists `queued → running → awaiting_validation` or `failed`. When `prepare_cmd` is set, that command runs on the host after the worktree is created and before the agent. Failure persists `queued` then `failed`, does not enter `running`, and stores the process exit code, or 1 when the process has none. A zero exit code is not story completion.

Explicit follow-up commands then run:

`awaiting_validation → tests → security → independent review → awaiting_documentation → documenting → awaiting_post_docs_validation → tests → security → independent review`

With no quality policy file, success ends at `awaiting_pr`. Failures persist as `blocked` or `changes_requested`. `pr-create` from `awaiting_pr` records `pr_created`. Nothing on this path merges or marks a story complete. `schedule-durable` also stops a successful agent at `awaiting_validation` when the policy file is absent.

With `.codehelm/quality.yaml` present, `schedule-durable` runs those gates inside the claimed attempt and then scores the contract. The manual post-documentation command does the same scoring. The task and the dispatch row become `blocked`, `awaiting_human_approval`, or `ready_for_pr`. `pr-create` is allowed only from `ready_for_pr`, and it evaluates the recorded evidence again before publishing. A failed gate does not launch the later model calls for that attempt.

Story completion in the durable scheduler is a separate step. It requires a recorded pull request, `--confirmed-merged`, and `gh pr view` reporting `state=MERGED` with a merged timestamp. An open or closed pull request does not complete the story. When a quality policy is active it also requires the latest evaluation for that attempt to be `ready_for_pr`. Dependents stay locked until that completion. `schedule-durable` merges one recorded pull request when `auto_merge` is true, every gate passed, required human approval is present, and every GitHub check is success. The plain `schedule` command does not. `merge-ready --execute` uses those same checks. A result that is not yet `MERGED` is a failure. That command does not mark the story complete. The durable scheduler posts a Jira transition only when `jira_transitions` maps the new state and the story has a `jira_key`. The mapping is off by default. `jira_transition_execute` is off by default, so the scheduler records a dry run and does not call Jira. A missing key or a Jira error is stored on the task and reported; the dispatch state stays as written. An explicit `jira-transition` command posts one transition id; a dry run does not call Jira.

## Durable scheduling

`DurableScheduler` stores one row per story. Claims use `BEGIN IMMEDIATE`. Limits:

- per-story attempts (default 2, maximum 5)
- total attempts per prefix (default 20)
- concurrent claims (default 2, maximum 8)
- estimated token and USD reservations in the same transaction as a budgeted claim
- optional additional-AUD monthly admission (warn A$10, critical A$15, pause A$20, epic A$5)

These are admission controls on estimates CodeHelm stores. They are not provider-side spending caps. Live token use is unknown unless a verified usage report is imported, structured CLI stdout is recognized by `parse_cli_usage`, or the opt-in HTTP transport returns a usage object `parse_usage` understands. Unknown usage is not stored as zero. HTTP is off by default and is not a spending cap.

A claim heartbeat refreshes `claimed_at` during the agent and, when a policy exists, between quality stages. If the lease expires, the story becomes `interrupted`. Recovery never relaunches a coding agent that is still queued, running, or failed. If the agent had already finished, the next `schedule-durable --execute` can resume that same attempt and skip gates that already passed. `schedule-retry` remains the way to start a new task id (`PREFIX-S1-A2`). Resume does not take a second budget reservation.

Lifecycle command timeouts are CLI options with today's defaults unless overridden. `schedule-durable` and `resume` pass `--agent-timeout` (default 600) into `carry_story` as the coding-agent and documentation-agent limit, and `--gate-timeout` (default 300) as the test/security/review limit. Manual `validate` and `validate-after-docs` expose a single `--timeout` (default 300) for those gate and review steps; `document` exposes `--timeout` (default 600) for the documentation agent. All of those options are bounded 1..7200. `run` and `agent-run` keep a separate `--timeout` with max 3600. Timeouts apply only when `--execute` runs the underlying process; they are not lease or spend controls. `prepare_cmd` uses a separate 900 second host timeout and does not follow `--agent-timeout` or `--gate-timeout`.

## Quality contract

Policy file: `.codehelm/quality.yaml` with `schema_version: 1`. If the file is absent, `load_policy` reports the contract inactive and existing commands keep their previous transitions. Omitted keys use defaults (tests, security, architecture review, independent review, documentation, acceptance criteria, 400 changed lines, and human approval for authentication, migrations, security-sensitive paths, and production infrastructure). `architecture_cmd` defaults to empty. When `risk_patterns` is omitted or null, a small built-in content scanner runs. A configured mapping replaces it, and `{}` turns content scanning off. `gate_runner` defaults to `namespace`. `gate_image` is required only when `gate_runner` is `container`; an empty or missing image in that mode fails closed. In namespace mode `gate_image` is ignored. A workflow publishes `ghcr.io/dannyyounes/codehelm` on pushes to `main` and on version tags. Pin `gate_image` to the digest that workflow prints. The gate does not pull it. Optional `base_branch` names the integration branch for change counting and for the default `pr-create --base` when that flag is omitted (`default_pr_base`). Set it when that branch is not `main` or `master`. Without it, committed changes on a repo whose only integration ref is outside the main/master fallbacks can count as empty after commit. `resolve_diff_base` picks the first existing ref in order `refs/heads/<base_branch>`, `refs/remotes/origin/<base_branch>`, `main`, `master`, `origin/main`, `origin/master` (each as `refs/heads/<name>` or `refs/remotes/origin/<name>`) so a tag cannot override a branch. `collect_diff` then counts `git merge-base <base> HEAD` through `HEAD` (`merge-base..<HEAD>`), then adds working-tree and untracked changes. The approval digest uses that same base. It is a cached binary diff of a temporary index after `git add -A`, so a commit that does not change content leaves it stable. A dirty submodule, an untracked nested repository, or a missing merge-base makes it empty. When no base resolves, it falls back to the uncommitted diff against HEAD, and a commit then changes it. `pr-create` does not walk that chain: it passes the policy string to `gh pr create --base`, or `main` when the key is absent. A present value must pass `git check-ref-format refs/heads/<name>` (not `--branch`); null, empty, non-string, `HEAD`, `@`, names starting with `-`, names containing `@{`, or other invalid names fail closed at policy load. `default_pr_base` returns that string (or `main`) and does not check that the branch exists; `gh` may still fail. An explicit `pr-create --base` still wins. Targeted coverage for that base is `tests/test_base_branch.py`. `pr_ready` defaults to false when the policy file is absent, the key is omitted, or the value is null, so `pr-create` passes `--draft`. `--ready` or boolean `pr_ready: true` omits `--draft`. `--draft` forces a draft even when both are set. A non-boolean fails closed with `pr_ready must be a boolean`. The CLI applies the key and the flags. `create_pull_request` and `publish_pr` default `draft=True` and do not read `pr_ready`. On execute the CLI pushes with `git push -u origin <branch>`, then runs `gh pr create`. A draft includes `--draft` immediately after `create`; a ready create omits it. Ready and draft creation never merge and do not call `gh pr ready`. Targeted coverage is `tests/test_github_pr.py`. `jira_transitions` defaults to off. A nonempty mapping is the only set of states the scheduler may post, and `jira_transition_execute` defaults to false. Unknown schema versions and unknown keys fail closed.

`prepare_cmd` is optional. Omitted, null, or an empty YAML key, it is empty and `execute` does not run a prepare step. A present value is an argv with the same validation as `architecture_cmd`: a nonempty list of nonempty strings and no NUL characters. An empty list, a bare string, an empty item, or a non-string fails policy load. There is no shell. When the list is nonempty, `LifecycleEngine.execute` runs it on the host immediately after creating the worktree and before the provider call, with cwd set to that worktree and a timeout of 900 seconds. The process keeps the operator's environment, including credential variables, and can use the network, so the operator can run a step such as `npm ci` or `composer install` from their own `quality.yaml`. `gate_runner` does not apply. The result is evidence gate `prepare` with source `command_gate`. Exit 0 lets the coding agent start in that worktree, which is still the base checkout plus files the command wrote. A nonzero exit, a timeout, or a failure to start the process marks the task failed and does not start the coding agent. The evidence detail stores the argv and the captured output, cut at 4000 characters. The evidence exit code is null when the process has none; the task exit code is then 1. When `carry_story` started that `execute`, it settles the story `failed` and returns before `run_contract_gates`. `assess` and `evaluate` do not read the row, so a missing prepare row does not change the contract decision. With `--execute`, `run`, `schedule`, and `schedule-durable` start the coding agent only through `execute` (`schedule-durable` only when that attempt has no task row yet). Both CLI and HTTP transports hit this step. A dry run does not. `agent-run` and `worktree-create` do not call `execute`. `execute` refuses an existing task id. `schedule-retry` starts a new task id and runs `prepare_cmd` again. `resume` does not relaunch a failed task. Targeted coverage is `tests/test_prepare_cmd.py`.

`TaskStore.initialize` is the migration. It creates `quality_evidence` and `quality_evaluations` with `CREATE TABLE IF NOT EXISTS`, adds any missing columns, and records state schema version 3 in `schema_migrations`. Version 3 adds `quality_evidence.signature`. Existing task and dispatch rows are left in place. `codehelm init` does not write a quality policy.

`validate`, `document`, `docs-exception`, `validate-after-docs`, and the durable quality wave append evidence. `schedule-quality` does not run those commands again. It and the post-documentation gate call `assess`, which reads only the current attempt. A `prepare` row written by `execute` is not one of these checks:

The approval digest is `sha256:` plus the hex sha256 of a length-prefixed payload. `quality-approve` and scoring both pass policy `base_branch` into `diff_digest`. When `resolve_diff_base` finds a ref, CodeHelm copies the index to a temporary file, sets `GIT_INDEX_FILE`, and runs `git add -A` on that copy (`.gitignore` is honoured). It then hashes `git diff --cached --binary --full-index --no-renames --no-color --no-ext-diff --no-textconv --ignore-submodules=none` of that index against `git merge-base <base> HEAD`. Diff text is pinned with `a/` and `b/` prefixes, `core.quotePath=true`, `diff.noprefix=false`, `diff.mnemonicPrefix=false`, and `diff.relative=false`. The hashed bytes are `diff <length>\n` plus that diff. The real index is not modified (`GIT_OPTIONAL_LOCKS=0`). Git runs without host config or credential environment variables. Committed changes since the merge-base and the current working tree, including untracked files, are in that one diff, so committing the same content leaves the digest unchanged. A content edit of a tracked or non-ignored untracked file changes the digest. When at least one approval is stored and none of them equal the new digest, scoring sets `approval_mismatch` and the decision is `blocked` with `approval_diff_mismatch`. A clean submodule pointer change (porcelain `C` only) is the gitlink commit id, not the files inside the submodule, and committing that pointer keeps the digest. A submodule with tracked modifications (`M`) or untracked content (`U`), and an untracked directory that contains `.git`, yield `""` because `git add -A` would record only a commit pointer. A missing merge-base or any Git error also yields `""`. `quality-approve --execute` then refuses with `Human approval requires a workspace diff digest` and writes no row. An empty digest is not `approval_diff_mismatch`; if human approval is still required the status stays `awaiting_human_approval`. When no base resolves, the payload is `git diff --binary --no-ext-diff --no-textconv HEAD` plus each untracked non-ignored path and its bytes (`file <utf-8-path-byte-length> <byte-length>\n`, the UTF-8 path, a newline, then the bytes). An unreadable untracked path yields `""`. That fallback does not include already-committed changes, so committing the approved work changes the digest and the approval no longer counts. Gitignored paths are omitted in both forms. A symlink contributes its target path, not the bytes of the file it points at. Approve and score must see the same `base_branch`; a different base produces a different digest. Approval digests assume an honest local workspace; adversarial tampering (symlink/TOCTOU races, hostile git filters/attributes) is out of scope by design. Targeted coverage is `tests/test_diff_bound_approval.py`.
`codehelm document` sends the base prompt. `schedule-durable` and `resume` append the story title, description, and acceptance criteria when `require_docs` runs the documentation agent. The added text tells the agent to respect any documentation scope or line limits stated there and to make no edit when documentation is already complete. Those limits are prompt text. Whitespace-only title, description, and criteria add nothing. Content hashes over the union of paths from `git status --porcelain -uall` before and after the agent decide which files the agent edited. A path that was dirty before and is clean or missing after counts as an edit. An edit outside documentation paths fails with `Documentation agent modified non-documentation files`. A documentation-only edit passes; the evidence detail is the agent stdout (last 2000 characters) or `Documentation changes detected`. Documentation paths are `README.md`, any path under `docs/`, a path ending in `.md` or `.rst`, or a path starting with `CHANGELOG`. When the agent exits 0 and edits nothing, the gate passes with detail `Documentation already included in the change` if `collect_diff` against the resolved base already includes one of those paths. That diff is `merge-base..<HEAD` plus working-tree and untracked paths. `base_branch` is read from `.codehelm/quality.yaml` beside the state database. A missing file or an omitted key leaves the name empty, so only the main/master fallbacks are tried. A named ref that is not present falls through to those fallbacks. Lookups use only `refs/heads/<name>` and `refs/remotes/origin/<name>`. The same no-edit case fails with `No documentation changes detected` when no documentation path is in the diff. A nonzero agent exit fails with `Documentation agent failed:` plus the provider stderr, last 1500 characters, and skips that diff check. On `document`, a policy-load error or `Could not compute the documentation diff against the resolved base` is stored on the docs row and the task becomes `blocked`; the task error is prefixed with `documentation:`. `schedule-durable` and `resume` load the policy before gates, so an invalid policy fails that command before this agent runs. If the diff check raises during a durable docs stage, the exception is stored on the docs row and scoring adds `documentation_not_verified`. The status check misses ignored files. It does see a dirty path the agent restores or deletes: a non-documentation path fails the gate. A commit that is clean in both snapshots is not an agent edit; if the agent exits 0 with no porcelain change, a documentation path already in the resolved-base diff still passes. Targeted coverage is `tests/test_documentation.py`.

`record_evidence` rejects any other source, including an agent-supplied JSON document. Outcomes are appended to `quality_evaluations` and copied onto the task and, from `schedule-quality --execute`, the dispatch row.

When any of `story_title`, `story_description`, `acceptance_criteria`, or `scope_text` is not `None`, `independent_review` builds a context block, cuts it to 12000 characters when it is longer, then appends the story-review instruction and the original code or architecture prompt. The block is the heading `Story`, the title, the description, a blank line, the heading `Acceptance criteria`, and one `- ` line per criterion. `scope_text` adds a blank line, the heading `Declared scope and threat model`, and that text. The cut applies only to the block, so it can split a line and omit later criteria. With all four values `None`, the prompt is exactly the original prompt for that kind. The verdict rule is unchanged: the last line must be exactly `APPROVED`, the reviewer must be a different provider, and the Git snapshot must be unchanged. CodeHelm does not classify findings as in or out of scope. The instruction asks the model to list out-of-scope or optional notes and still end with `APPROVED`.

`validate` and `validate-after-docs` call `_story_review_kwargs` only with `--execute`. That helper reads `.codehelm/plan.json` and `parse_resume_task_id` (`PREFIX-STORY-An`: prefix and story id are `[A-Za-z0-9_]+`, and the attempt is `A` plus an integer that does not start with `0`). On a match it passes `story_title`, `story_description`, and `acceptance_criteria` from the story whose `id` is the middle segment. It does not pass `scope_text`. A missing file, `ValueError`, `PlanningError`, `OSError`, or an unknown story id returns an empty mapping, so the prompt stays the base prompt and the command continues. `validate` forwards those keywords to the code review. `validate_after_docs` forwards them to the code review and to the architecture review when that review runs. `carry_story` passes the same three fields from the scheduler story into `run_contract_gates`, which forwards them to every code review and architecture review in the wave. `schedule-durable` and `resume` both use `carry_story`. The description is copied whole; phrases inside it are not parsed. `schedule-quality` and `quality-eval` do not call `independent_review`.

Verify with `pytest tests/test_quality.py::test_review_prompt_unchanged_without_story_context tests/test_quality.py::test_review_prompt_includes_story_context tests/test_quality.py::test_story_context_is_truncated tests/test_quality.py::test_validate_passes_story_context tests/test_quality.py::test_validate_cli_passes_plan_story tests/test_durable_quality.py::test_carry_story_sends_plan_story_to_reviewer`.

`schedule-quality` still refuses an interrupted story. Resuming it first re-claims the same attempt; `schedule-retry` starts a new attempt, and only that new attempt's rows count.

High-risk classification uses path globs. When `risk_patterns` is omitted or null, a built-in scanner also checks changed files for a PEM or OpenSSH private-key header, an `AKIA` access-key id, a `ghp_` or `github_pat_` token, and a line that drops a table or column. A configured mapping replaces that set. `risk_patterns: {}` turns content scanning off. A match is a heuristic, not proof of a secret or a migration, and the scanner does not detect every risky edit. Path globs still apply. A risky change outside those globs and the active content patterns is not detected unless an operator records a `risk` row. `quality-approve --execute` stores the GitHub login and the approval digest described above. It refuses an empty digest and does not modify the real index. Committing the same content leaves that digest unchanged only when a base resolved. A content edit makes that approval not count. When no base resolves, committing the approved work changes the fallback digest. With `approval_signature` off, that row is not a cryptographic signature. `approval_signature: required` demands an SSH or GPG signature over the digest, checked again when the story is scored. Evaluation does not repeat the GitHub call. Test and security commands run in a private user, mount, pid, and network namespace. The workspace stays writable; `/tmp`, `/home`, and `/root` are covered, and there is no unsandboxed fallback. A host that blocks unprivileged user namespaces refuses the gate. The coding agent and the model reviewer stay outside that namespace. `prepare_cmd`, when set, also stays outside it: no shell, the operator's environment including credential variables, and the operator's network. Each quality debt accepts one unresolved finding for the current attempt. More than one debt can be recorded. `quality-debt` stores that finding as detail and a nonempty reason as identity (`source=human`, passed). Evaluation drops a finding only when its text matches. A debt from another attempt does not count, and a debt whose text does not match a finding is ignored. The debt does not waive tests, security, review, architecture, docs, acceptance, or human approval. The namespace sandbox is not a container image. An optional container runner is off by default. When `gate_runner` is `container` and the local runtime or `gate_image` is unavailable, the gate fails closed and the command does not run on the host or through the namespace sandbox. That runner does not pull an image and does not fall back to the host. A workflow publishes `ghcr.io/dannyyounes/codehelm` on pushes to `main` and on version tags; pin `gate_image` to the digest it prints. CodeHelm does not fetch that digest. The image supplies Python, pytest, and bandit, and it does not run the coding agent or the model reviewer. Architecture review reuses the independent-review function with a different prompt; it is still a model verdict. When that review is required, an optional `architecture_cmd` runs first and must also exit 0. It does not replace the review, and turning the review off skips the command. `max_retries` on the policy is not a second retry loop. `DispatchBudget` remains the enforced attempt cap. An omitted `--max-attempts` uses `policy.max_retries` when the policy file exists.

## Budgets and provider use

Token and USD figures are reservations plus optional reconciliation of a verified provider JSON report. Missing fields fail closed. AUD controls apply to an explicitly supplied additional-charge estimate, or to a USD amount multiplied by an operator-supplied AUD-per-USD rate and a source label. `--fetch-aud-rate` is off by default. It reads AUD per USD from frankfurter.app, stores that source and the rate date, and fails closed when the fetch fails or the date is more than five days old. There is no default rate. `--convert-reserve-usd` is off by default. With `--fetch-aud-rate` it converts `--reserve-usd` into the AUD charge and refuses `--additional-usd`. The USD reservation is still stored as USD. `plan-publish --execute` writes returned story keys into the plan; a dry run does not, and an existing `jira_key` is refused. Do not describe any of these as guaranteed spend protection.

## DesignFlow

DesignFlow is a local mockup loop, separate from story dispatch. Screens and comments live in `.codehelm/designflow.db`. HTML files live under `.codehelm/designflow/<screen-id>/`. A draft built from `--field` or `--spec` does not call a provider. `--execute` on `draft` or `revise` does, through the same CLI or HTTP provider adapter as the rest of Codehelm. HTTP stays opt-in and does not fall back to the CLI.

The provider must return one JSON object with `title`, `brief`, and `fields`. Unknown keys, code fences, and raw HTML are refused. The renderer escapes every string it places in the page. The only script in that page is the review client, which posts comments to the loopback server. `send` marks comments queued. `revise --execute` consumes queued comments after the new spec validates. Comments that were not sent stay on the mockup. A failed agent response does not advance the revision.
